# Decisions

Short entries, newest last. Note what was decided, why, and anything verified in Apple's docs (with the date checked).

## D1: The JSON Schema is the contract
`schema/passclip-import.v1.schema.json` defines the import format. The prompt, examples, TypeScript types and validation all follow it. Changing a field means bumping `schemaVersion`.

## D2: Website first
A web drop site ships faster than an iOS app: no App Store review, and Safari on iPhone can add passes to Wallet directly. The iOS app, Siri and email import come later and reuse the same pass engine.

## D3: Bring your own AI, for now
Users run the extraction in any AI chat with our prompt. Built-in extraction (an API call or Apple's on-device models) can replace that step later without changing the import format.

## D4: Barcodes are never AI-generated
A wrong barcode makes a pass useless at the door. Barcode data comes only from text in the source or a real scan, and the user confirms it.

## D5: Milestone 0 scaffold (2026-10-03)
- `create-next-app` 16.3.8: Next.js 16.3 (App Router, Turbopack), React 19.2, Tailwind 4, ESLint 9. Next.js 16 differs from older versions (`next lint` is gone, `middleware` is now `proxy`, request APIs are async). The `AGENTS.md` that `next dev` maintains points to the docs bundled in `node_modules/next/dist/docs/`, and `CLAUDE.md` imports it.
- TypeScript 5.9, which the template pins. TypeScript 7 works with `next build` but has no compiler API yet, which editor plugins and other tools rely on.
- `npm run typecheck` runs `next typegen` before `tsc`, because Next's route types and `next-env.d.ts` are generated and not committed.
- Vitest 5 runs the tests in Node. Vite resolves the `@/` imports from `tsconfig.json` by itself, so no plugin is needed. Component tests (jsdom) can come with the Milestone 1 UI.
- `@types/node` 22, to match Node 22 and the versions Vitest 5 supports.
- `npm audit` reports 5 high-severity advisories, all from one package (`braces`) inside `eslint-config-next`'s lint tooling. That code never reaches the site, and the suggested fix downgrades `eslint-config-next` to v14, so it stays until Next.js updates its dependency.

## D6: TypeScript types come from the schema, minus rules types can't express
`npm run gen:types` uses json-schema-to-typescript. On its own it turns `if`/`then` into a duplicated intersection type and `maxItems` into lists of tuples, so the script first removes conditional keywords (`allOf`, `anyOf`, `if`/`then`, `dependentRequired` and similar) and keeps arrays plain. The types are slightly looser than the schema (for example, `transit` is optional on every pass type), and Ajv still enforces the whole schema. A test fails when `types.ts` is out of date.

## D7: One module for the signing settings
`src/lib/pass/signing.ts` reads and decodes the signing env vars. `npm run check:env` uses it now, and Milestone 2's pass builder and preview-only mode will too. The check opens the certificate and key with Node's `crypto` module and confirms that the key belongs to the certificate, that the WWDR certificate issued it, and that nothing has expired. Tests create throwaway certificates with OpenSSL, so no certificate is ever committed.

Checked in Apple's docs on 2026-10-03: WWDR G4 is the intermediate certificate for Pass Type ID certificates (Apple Developer Account Help, "WWDR intermediate certificates"). `check:env` doesn't hard-code a generation. It checks that the given WWDR certificate really issued the pass certificate, and if not, names the generation shown in the pass certificate's issuer.

Not confirmed in Apple's docs yet: that the pass certificate's subject holds the pass type ID in `UID` and the team ID in `OU` (the usual layout for Apple's service certificates). `check:env` fails only on a mismatch and adds a note if those fields are missing. Confirm with the real certificate before Milestone 2.

## D8: Browser validation must work under a strict CSP (to do in Milestone 1)
Ajv turns the schema into JavaScript at runtime. A strict Content-Security-Policy (SPEC §11) blocks that in the browser unless it allows `unsafe-eval`. Milestone 1 should precompile the validator with Ajv's standalone code generation (a generated file, like `types.ts`) rather than loosen the CSP. `src/lib/import/validate.ts` compiles at runtime for now, which is fine for scripts and tests.

## D9: The iPhone app comes right after Milestone 2 (2026-10-03)
The owner wants a native app as well as the website. The website still goes first, through Milestone 2, because the app needs the same server to sign passes (the signing key can't ship inside an app) and the website gets real passes working soonest. Then the iOS app starts: its share sheet and on-device extraction are what beat iOS 27's built-in pass creation. M3 to M6 stay, kept small, and are scheduled around the app. App work needs a Mac with Xcode, so it's best done with Claude Code on the owner's Mac.

## D10: Validation runs in the browser, and clean-up is a bit more lenient (Milestone 1, in progress)
- The schema validator is precompiled by `npm run gen:types` (Ajv standalone code with its one runtime helper inlined), which resolves D8. Ajv's own error messages are left out, because `messages.ts` writes plain ones.
- Before validation, Passclip also drops empty values (null, "", {}, []) and attachments without a full https link, with a warning. AI replies often contain empty values, and SPEC §3.3 asks for removing non-https links rather than failing. Passes are never dropped, so pass numbers in messages match the JSON.
- Warnings carry a kind: things Passclip already fixed (`kind: "fix"`) can be shown more quietly than things the user should check.
- Status and next steps: `docs/HANDOFF.md`.

## D13: Checked Apple's Wallet docs: semantic tags, relevance and image sizes (2026-10-03)
Apple's documentation was reachable from this session (developer.apple.com, through its JSON documentation pages). Checked on 2026-10-03:
- **Semantic tags** (`SemanticTags` and its types): `src/lib/pass/semantics.ts` now adds them, only with data from the import and only for the pass styles Apple lists. Event tickets get event name, venue (name, coordinates, room, entrance), start and end, duration in seconds, attendee name and seats. All boarding passes get provider, confirmation number, boarding group, original departure/arrival/boarding dates, duration, departure/destination coordinates and seats. Flights add the airline-only keys (airline code, flight code, numeric flight number, airport codes and names, cities, gate, terminals); trains add the rail-only keys (station names, platform, car number). Buses, ferries and trains get `vehicleNumber`; flights don't, because Apple means the aircraft, not the flight. Store cards get `balance`. Any pass with a price gets `totalPrice`. Money amounts are strings, as Apple documents.
- Differences from SPEC §4.6: Apple lists `confirmationNumber` for boarding passes only, so event tickets don't get it. The flight code and number are only split out when the printed number clearly matches the airline code ("ZQ 101" with ZQ); otherwise they're left out rather than guessed. `passengerName` needs given and family names, which would mean guessing how to split a name, so it's left out.
- **relevantDates**: entries have `startDate` + `endDate` (or a single `date`), from iOS 18; `relevantDate` is deprecated. Apple documents no maximum interval length, so the earlier code comment claiming a 24-hour limit was wrong. Multi-day events still keep only the legacy `relevantDate` until a device check shows how longer intervals behave.
- **Image sizes** (Human Interface Guidelines, Wallet): the icon is 38×38 pt for every pass style, and the logo is 50 pt tall and 50–160 pt wide, as PNG at @2x and @3x. The placeholder icon was 29×29 (an older size); it's now 38×38 with an opaque background, because the icon shows in notifications.
- The boarding pass description now reads "Boarding pass from Tokyo to Paris", as SPEC §4.1 asks.

## D15: Milestone 3, the barcode helper (2026-10-03)
- Each pass card can read codes from a screenshot or photo, on the device: the image is turned into pixels in the browser and never sent anywhere (browser tests watch the network to prove it). Up to 25 MB; big photos are scaled to 2400 px on the long side, and phone photos are turned upright first.
- Decoding uses `@zxing/library` directly (the engine `@zxing/browser` wraps), so the decoder is a pure function tested in Node with real images from bwip-js. It calls the four format readers one at a time, because ZXing's combined reader prints a console warning for every format it doesn't find.
- ZXing finds Aztec codes by looking out from the middle of the image, so it missed codes off to one side or next to another code. The decoder now also finds dark, code-like areas and reads each on its own, and lists codes in reading order. It retries with inverted colors for dark-mode screenshots.
- Nothing is used until the person taps **Use this code** (CLAUDE.md rule 3). The chosen code is written into their JSON, so the preview, the pass and the text box can't disagree. If the JSON already has a different code, both are shown and the person picks; a matching one is confirmed. Typed codes are allowed, with a warning that one wrong character makes the pass useless. The old text under the code is kept only if the code itself didn't change.
- When a pass already has a barcode, checking it against a screenshot is optional, so that part starts folded away.
- iPhone photos in HEIC open in Safari but not in Chrome; the error message suggests a screenshot instead.
- Checked in Apple's docs on 2026-10-03 for SPEC §7's new barcode types: the format strings are `PKBarcodeFormatCode39`, `PKBarcodeFormatCodabar`, `PKBarcodeFormatEAN13` and `PKBarcodeFormatI2of5` (ITF), and from iOS 27 a pass may list more than one barcode as a fallback for older iPhones. Adding them is schema v1.1, which needs the prompt, examples, app and decoder changed together; it isn't done yet.

## D16: Milestone 4, Add to calendar (2026-10-03)
- `src/lib/calendar/ics.ts` turns a pass into one RFC 5545 event: times in UTC (so no time zone definitions are needed and every calendar shows the right local time), text escaped, lines folded at 75 bytes without splitting characters, CRLF line endings. Every generated file is parsed back with `ical.js` (the standards-based parser Thunderbird uses) in the tests.
- The details follow SPEC §8: offered for passes with a start (event tickets and travel by default; `calendar.add` decides otherwise). Events last two hours unless the import says; trips last until arrival, or one hour. Reminders: two hours before events, three before flights, 30 minutes before trains, buses and ferries, or the import's own `calendar.alertMinutesBefore`. Flights and trains are titled with their number, like "ZQ 101 Tokyo → Paris". The location is the venue or the route; the description lists the seat, gate or platform, confirmation code, notes and links. Coordinates become `GEO`.
- One deliberate change from SPEC §8: the event ID comes from a hash of the pass's details rather than a random serial number, so adding the same pass again updates the event instead of duplicating it, without spelling out ticket details.
- `/api/ics` runs on Node, is reached by a real form navigation like Wallet passes, and reuses the import checks (size limit, same-site only, rate guard). It needs no signing, so it works in preview-only mode. Nothing is stored or logged.
- Still to check on devices: that the file opens in Apple Calendar on iPhone and Mac, and in Google Calendar, with the right local times and alerts. The download is sent as an attachment; if iPhone Safari doesn't offer to add it to Calendar, try `inline`.

## D18: Rate limits per visitor, using only headers visitors can't fake (2026-10-03)
- The first limiter gave the whole site one budget of 30 requests a minute, so it couldn't be fooled by a forged IP address. But one visitor sending 31 requests a minute would have locked everyone else out, and normal traffic above 30 passes a minute would have been refused.
- Now each visitor gets 30 a minute, keyed by an IP address only the host can set. Vercel's docs (checked 2026-10-03) say it overwrites `X-Forwarded-For` to prevent IP spoofing, and `x-vercel-forwarded-for` carries the same value even behind another proxy. So on Vercel (`VERCEL=1`) the limiter uses that header automatically. Other hosts name theirs in `RATE_LIMIT_IP_HEADER`, such as `CF-Connecting-IP` behind Cloudflare. Without either, everyone shares one budget as before, because any other header could be forged.
- Counts live in each server instance's memory, and old entries are dropped once 10,000 visitors are tracked. For one limit shared across instances, add a rate-limit rule at the host.

## D19: File attachments go straight to an S3-compatible bucket, with nothing stored about them (2026-10-03)
- Milestone 5 (SPEC §9). People attach a PDF, JPEG, PNG or HEIC file (up to 10 MB, 5 per pass) and its https link goes into the pass's `attachments`, so it shows on the back of the pass like any other link. The file is never put inside the `.pkpass`.
- Files go from the browser straight to the bucket. Vercel's docs (checked 2026-10-03) limit a function's request body to 4.5 MB, so a 10 MB file can't pass through the site. `/api/attachments` receives only the file's name, type and size, checks them, and signs a 10-minute upload link. The link signs the exact type and size, so it only accepts that file.
- Any S3-compatible storage works: the settings are the six `STORAGE_*` names in `.env.example`, and uploads stay off until all are set, like signing. Supabase Storage is the example in docs/LAUNCH.md, because SPEC §9 names it and it needs no CORS setup: its S3 endpoint answered a browser preflight on 2026-10-03 with `Access-Control-Allow-Origin: *` and allows PUT with `Content-Type` (Supabase doesn't support per-bucket CORS rules, its S3 docs say). R2 and AWS S3 need a CORS rule.
- Upload links are AWS Signature Version 4 presigned URLs, made with Node's crypto (`src/lib/storage/sigv4.ts`) rather than the large AWS SDK. Tests check them against AWS's documented example and against signatures made by the AWS SDK (`@aws-sdk/s3-request-presigner` 3.1146.0) for Supabase-, R2- and local-style addresses. The query matches the SDK's (`X-Amz-Content-Sha256=UNSIGNED-PAYLOAD`, `x-id`), since storage services test against it. The browser tests run a fake bucket that checks every signature against the headers the browser really sent.
- Nothing about an upload is stored: no database, no accounts. Each file gets a random 256-bit delete token. Its folder is the first 128 bits of a hash of that token, so the public link is unguessable but can't be turned back into the token, and the token alone finds the file. The delete link is `/delete-file#<token>/<file name>`: browsers never send what follows `#` to a server, so the token stays out of server and host logs until the person confirms on the page, which then sends it once in a form POST. The page shows the link once, with a copy button, and the privacy page explains this.
- Same-site checks now accept `Sec-Fetch-Site: same-origin` on its own. Browsers set that header and pages can't change it. The Origin can't be compared reliably: Next reports `localhost` when the server listens on `127.0.0.1`, and the browser sent the real address for the upload's fetch. Requests without the header (older browsers, the iOS app) still need a matching Origin.
- The page's Content-Security-Policy adds the storage address to `connect-src` only when uploads are set up.
- `npm run check:storage` tries a real upload, public read, CORS preflight and delete with the owner's settings. It still needs an iPhone check: attachments opening from the back of a pass in Wallet, including HEIC photos.

## D20: Over-long display text is shortened, not rejected (2026-10-06)
- A real AI reply had an 81-plus character event title, and the whole import failed with "title is too long". That broke "lenient in" (CLAUDE.md rule 5) for something Passclip can fix safely.
- Text that people only read (title, subtitle, notes, venue name, seat description, extra fields, warnings and similar) is now shortened to the schema's limit at a word boundary, ending with "…", with a warning to check it. The limits are listed in `clean.ts`, and a test checks them against the schema.
- Codes, IDs, names, times, links and barcodes are never shortened: a cut confirmation code or barcode would be wrong, not just short. Those stay errors to fix.

## D22: The iPhone app reads a pasted email with Apple's on-device model; the pass front shows more (2026-10-07)
- Why: the copy-the-prompt, paste-the-reply flow works on the website but is clumsy on an iPhone. The app now reads the email itself with Apple's Foundation Models framework: free, private, works offline, no API key. SPEC §15 planned this ("On-device extraction").
- How it works: the person pastes (or shares from Mail, Safari or Notes) the email text. `EmailPreparer` trims it to fit the model's small context (docs say 4K tokens, 8K on newer iPhones in iOS 27.0, checked 2026-10-07): quoted replies, tracking links and repeats go, then the longest paragraphs without numbers. The model fills a small guided-generation type (`GeneratedPass`); `ImportJSONBuilder` turns it into import JSON (schema 1.1). That JSON shows in the box, is editable, and goes through the same server preview as any pasted reply. Dates, time zones and types it can't trust are left out with a warning, never guessed.
- The model has no barcode fields and is told never to write one (CLAUDE.md rule 3). The barcode still comes from a screenshot the person chooses. A web test (`tests/ios-fixtures.test.ts`) runs the Swift builder's golden file through the server's pipeline, so the two can't drift apart.
- Who can use it: iPhones with Apple Intelligence turned on (iOS 26 or later). Others see why, and keep the copy-the-prompt flow, which is unchanged. The framework is weak-linked, so the app still launches on iOS 17 and later.
- Private Cloud Compute is not used yet. iOS 27 lets apps use Apple's server model (32K context, free for apps under 2 million first-time downloads, per-user daily quota) but it needs a managed entitlement that Apple grants on request (developer.apple.com/private-cloud-compute); it needs the same eligible devices, so it wouldn't reach more people, only handle longer emails. Worth requesting before launch.
- Not tested here: this Mac reports the model as unavailable (`deviceNotEligible`), so the generation itself has only been checked by building against the iOS 27 SDK and by running everything around it, with a debug-only stand-in (`PASSCLIP_FAKE_AI=1`). Quality on real emails needs a check on an iPhone.
- Pass front: event tickets now show the seat category (like "CAT 2") and the booking number on the front when the lower row has room, and not again on the back. A real ticket without a seat number was nearly empty in Wallet.
- Correction to an earlier note: the preview's date format isn't a bug. It follows the device's region settings, like Wallet does; the Simulator on this Mac uses Canadian settings, which write `2026-10-10`.

## D23: PDFs and screenshots in the iPhone app

- The Share sheet now accepts PDFs (including "Print → Share" from a preview), screenshots, photos and any file, and the in-app picker shows every file. The kind comes from the file's bytes (`%PDF-`, image data, UTF-8 text), never from its name, so a PDF saved without ".pdf" works. The first picker only allowed .json and .txt, which greyed out real tickets.
- A PDF's text goes through the same "Make pass" step as a pasted email. If the PDF has almost no text (a scan), the pages are read with Apple's text recognition. Everything happens on the iPhone.
- Barcodes in a PDF or image are found with Vision and offered as "Use this code". They are never added automatically (CLAUDE.md rule 3).
- Not handled: .eml and .html email files. Share the email's text instead.
- Not tested here: Vision doesn't run in the Simulator, so scanned-PDF reading and barcode finding need a real iPhone. PDF text reading is unit-tested.

## D24: Short titles and one-code auto-add (iPhone app)

- The model is asked for a title under 60 characters, and the app also shortens it (drops a trailing "in <city>", then cuts at a word and adds "…"). The full name goes first in the pass notes. A first real ticket gave an 80-character title that Wallet cut off.

With several codes or passes, the person still taps "Use this code". The code is always a real read from their document (CLAUDE.md rule 3), never from the AI.

## D25: Trust checks, links and pasted web links in the iPhone app

- **Why the title turned Chinese.** The model's instruction said "drop translations", and the SISTIC PDF lists the title in English and then in Chinese, so the model kept the Chinese line and dropped a character from it (三十 became 三). Now the model copies the first language only and also gives a short title taken from it. The short title is used only when all its words are in the full title (`SourceCheck`), and the full name goes first in the pass notes.
- **Every copied value is checked against the text it came from** (`SourceCheck`). A near miss is repaired from the text (the Chinese title above), and a booking number, name, venue, seat or code that isn't in the text at all is left out with a warning, so a slip can't become a wrong value on a pass. Dates and times are written differently from the text, so they still rely on the "Check every detail" warning. Notes that are only a timestamp or an address are dropped: the model had put a PDF's print date in the notes.
- **The pass says where it came from.** `source.kind` is now `pdf`, `screenshot`, `webpage`, `other` or `email`, with the file name or page title as the subject ("Imported from SISTIC E-Ticket"), not always "email".
- **Links to the original.** Links in a document go on the back of the pass as `attachments` only when the person switches them on (the first is on). They are found by a plain rule, not by the AI, in the PDF's text (Safari prints the page address in the footer) and in its link areas; terms, privacy, social and app-store links are skipped, and a link needs "ticket", "download", "order", "booking" or similar in its path, not its host. The link may carry an access token, but anyone holding the pass already holds the barcode, which grants the same access.
- **Pasted web links.** A web link pasted into the box, or a page shared from Safari, is opened from the iPhone with an ephemeral session (no cookies, https only, 25 MB limit), as Safari would. A PDF or image is read as above; a page is turned into plain text. Pages that need a sign-in, or draw their text with scripts, say so and point to Safari's Share, Options, PDF. Nothing from the page goes to Passclip except the pass details. The privacy page says so.
- **Time zone from the place.** If the model leaves the zone empty and the city names exactly one zone ("Singapore" is Asia/Singapore), the app uses it, so fewer people see the time-zone card.
- **Barcode reminder.** "The barcode isn't included" is no longer shown when a barcode was read from the document.
- **Not done.** Forwarding an email to a Passclip address needs a server that receives mail and a server-side AI, which breaks "your email stays on your iPhone", so it isn't built. Not tested here: the model itself (this Mac can't run it), Vision on scans and barcodes, and opening real ticket links; those need a real iPhone.

## D26: A designed picture and a different color for every event ticket (2026-10-10)

- **Why.** The real Wallet pass of a SISTIC ticket was one flat purple card with a large empty area between the fields and the barcode, and every event looked the same. The owner asked for "random color or something about design" and said "the down part is too empty".
- **What Apple says (developer.apple.com, checked 2026-10-10).** Event passes can show logo, strip, background or thumbnail images. A strip can't be combined with a background or thumbnail. The background is 180 × 220 points, "cropped slightly on all sides and blurred", and wants @1x, @2x and @3x files. Newer poster event tickets ("posterEventTicket", iOS 26) are not an option: Apple says they "aren't compatible with tickets that require a QR code or barcode for entry", and these tickets need a barcode.
- **What we do.** An event ticket whose colors are dark gets a `background.png` (+ @2x, @3x) drawn from its own colors: a deep gradient with soft glows and two faint rings, heavier toward the bottom where the card has no fields and calm at the top where the title sits. It is made in plain TypeScript (`artwork.ts`, `png.ts`, no image library and no outside images), so the same colors always give the same picture. Files are 10 to 70 KB. The neutral logo is left out because it would sit on the picture with nothing to say; the organizer's name (`logoText`) is shown instead.
- **Readable by construction.** No pixel may be brighter than what lets the pass's text and label colors keep 4.5:1 contrast (and never above 0.085 luminance, 0.11 for greens, which look dull otherwise). A test checks every pixel for 120 designs. Light passes get no picture and keep the flat color.
- **Random colors.** An event ticket with no colors of its own gets a deep color scheme picked from a seed made of the organizer and title (`designColors`): the same event always looks the same, different events differ. Colors the person gives are used as they are, and the picture is drawn in them. Other pass types keep their fixed colors for now.
- **Previews.** The iPhone app gets the 1x picture from `/api/import` (`artwork`, base64) and draws it blurred behind the card; the website draws the same plan as CSS gradients. Both are approximations of Wallet's blur, not pixel copies.
- **Starts shows only the time.** The header already shows the date, so "Starts" now shows the time alone (and is left out for all-day events), which also stops the date and the venue running together.
- **Not tested here.** How Wallet itself draws the blurred picture behind the fields needs a real iPhone; the guarantee above makes the text readable wherever it lands.
